# WiX transition: constraints and verification

This directory is under development. `bundle.wxs` creates a WiX Burn executable containing a real MSI; it is not yet a release installer. Do not publish the fixture or point the release workflow at it.

## Required behavior

- MSI owns the actual application files, stable installation path, repair, upgrade, removal and Windows Installer records. Burn embeds that MSI and the existing `assets/liukai.ico`, producing `LiuKai-win-setup.exe`.
- TSF registration uses Windows APIs. Machine-wide COM/profile resources and the interactive user's HKCU state require explicitly validated security contexts: MSI's elevated service context must never silently substitute SYSTEM's HKCU for the initiating user.
- Validate ownership, active sessions, existing file and registration state and legacy durable journals before migration. Never overwrite foreign data, erase old transaction history or use recursive registry deletion as a recovery shortcut. Existing user settings and backups must survive.
- The user has explicitly waived restoration of the previous version after a failed upgrade. Preserve unrelated user data, and verify that failed registration or removal leaves actionable evidence and does not silently claim success.
- MSI owns the files it installs; do not simply put the legacy custom installer inside an MSI. Preserve release manifest provenance, signatures/hashes and machine-readable diagnostics.
- Use standard MSI logs and validate MSI with ICEs. Verify the bundle's embedded MSI and icon and the actual downloaded GitHub artifact. Include clean install, upgrade, uninstall, reinstall, locked DLL, partial failure, rollback and interactive-user state checks; inspect both machine and actual interactive-user views.

## Observed R63 issue on this machine

Interactive launch and automation have the same user SID but observe different registry contents. The interactive R63 diagnostic reports absent TSF profile but an HKCU profile leaf and an owned profile marker; it returns 0x8007051A and refuses deployment. An earlier automated uninstall reported success in its own execution environment. Both runs reported the same user SID. The interactive history probe returned history_inspection=0; this verifies the machine-COM ledger classifier only, not all legacy histories. The source of the registry-view difference is not established. Do not clean or report success using only the automated view; collect and back up the real interactive view, verify transaction state and the exact owner before any recovery.

## Recovery policy under development

`legacy-recovery-policy.ps1` is a pure guard with no writes. The associated tests reject foreign identity, uncertain machine history, active installation files, unexpected registry values or subkeys, foreign ownership and non-absent registration resources. This policy alone cannot clean the machine.

`legacy-recovery-transaction.ps1` implements adapter-based sequencing. Isolated tests exercise successful completion, backup refusal, state drift, deletion failure and readback failure. The registry adapter and durable backup support resuming an interrupted cleanup; this recovery is not yet integrated into the MSI.

On 2026-10-29, the subsequently implemented recovery adapter was executed interactively on this machine. It reported successful removal of the two narrowly identified user registry leaves after saving a hashed backup. A separate interactive identity probe then reported that the registration resources and owner marker were absent. This verifies this machine's cleanup; it does not establish that migration is integrated into the MSI or safe for other machines.

The current disabled layout additionally includes the source package manifest as `versions/<version>/package-manifest.json`, under MSI ownership. The builder requires that manifest and the registration tool to be bound by the source release manifest. A fresh development build verified all 14 embedded payload files against their source hashes, the embedded MSI and the EXE icon. The manifest supplies identity evidence; it does not itself provide a registration transaction or recovery.

The disabled MSI now authors a fresh-registration custom action after InstallFiles. Its initial implementation checks the elevated process identity, intended Program Files root, legacy journals and raw profile leaves, and invokes the durable fresh-registration backend. The build embeds its validated runtime version and manifest SHA-256 in that action; registration rejects a different version or manifest hash. The action has only been compiled and table-validated; no Windows TSF mutation or runtime manifest rejection has been tested through it. MSI rollback, uninstall and user-context provenance still require implementation and verification. Do not enable or publish the package.

The seven-resource backend does not register the immersive-support or input-mode categories that the R63 release independently registers and checks for modern hosts. `modern-categories.hpp` adds a guarded transition, a durable observer, and conservative partial recovery for those categories, with isolated add/remove and failure tests. ## MSI context investigation

`context-probe.cpp` and `context-probe.wxs` form a diagnostic MSI which logs SID, elevation, session and presence of the user ownership marker from immediate, deferred impersonated and deferred system custom actions. The checked-in package remains deliberately blocked from installation. A separately built disposable fixture installs only a test file and is intended to record actual Windows token behavior before automatically uninstalling. A service-context HKCU must not be assumed to be the interactive user. On Terminal Server Microsoft documents that deferred actions can instead see the system hive unless terminal-server-aware.

On 2026-10-29, the corrected disposable fixture was launched from the interactive desktop after UAC approval. Its install and uninstall both returned 0, the product was absent afterward, and its test directory was removed. The MSI log shows that both the immediate action and the deferred impersonated action used the elevated desktop user process token; the deferred non-impersonated action used the SYSTEM process token. This is an observation for that invocation only: it does not establish behavior for a non-elevated launch, a different administrator account, Terminal Server, repair, or uninstall. Registration actions must verify their effective token and target user rather than infer them from this single test.

## Interactive machine lifecycle tests, 2026-10-30

The first test MSI installed and registered successfully but its custom-action host hung during DLL unload. A native stack showed MinGW pthread TLS cleanup waiting during detach. After targeted recovery, Windows Installer recorded a successful install; the user confirmed conversion in Search and Microsoft Store. The same old custom-action DLL hung during uninstall after both registration removal journals had committed. A targeted, identity- and stack-checked recovery allowed MSI to finish uninstall; MSI returned 0 and removed its product record and installation root. These results do not prove the old DLL completes normally.

The custom-action override now uses a trivial thread-local pointer with scoped ownership instead of a thread-local `std::wstring`. The dedicated DLL-detach regression reproduces the old hang and completes with the fix. A newly built test MSI with the fixed action passed WiX validation and the 14-file payload verification. On the same interactive account it installed without intervention (MSI exit 0, product state 5), with the base and modern registration journals committed; selected installed binaries matched their source hashes. The user confirmed input in Search and Microsoft Store, including longer English input. The same fixed test MSI then completed uninstall without intervention (MSI exit 0, product state absent, installation root and machine identity absent); both registration-removal journals report committed success. MSI reported a pre-existing pending reboot state. A separate read-only probe launched in the interactive desktop account returned success and reported the user and machine COM resources, profile, keyboard, tray and UI categories absent. The production prototype remains deliberately disabled, and migration, upgrade, repair, rollback, locked-file behavior and release delivery are not established by this test.

The existing release preflight and the DLL-detach regression passed after this test. The current production release workflow has not been switched to the development MSI.

On 2026-10-30 the user waived automatic restoration of the previous version after an upgrade failure. The current default RemoveExistingProducts schedule removes the old MSI before the new transaction starts; this is an accepted limitation, not evidence of upgrade success or old-version rollback.

The fixed MSI was also installed and removed through its Burn EXE in the interactive account. MSI reported success for both actions, the product record and installation root were absent afterward, and both removal journals committed. The working-tree release workflow now builds the WiX bundle and MSI, with the UI logo, notice, payload hashes and MSI validation checked. It has not yet been pushed or executed by GitHub. Automatic diagnostic ZIP collection and general legacy recovery are not integrated into the WiX bundle.

The development MSI now embeds the narrowly scoped legacy recovery scripts, a freshly compiled read-only legacy history probe and the existing diagnostic collector as MSI Binary resources. The package verification extracts each of the 11 Binary resources and checks it against its source hash. The collector accepts explicit WiX/MSI log paths and reports product registration failure stages; an isolated test validates the resulting ZIP and parsed HRESULT. These resources are not yet invoked by the WiX lifecycle: embedding them alone does not provide automatic recovery or automatic failure collection.

On 2026-10-30 an interactive MSI fixture intentionally failed after InstallFiles and before registration. The rollback custom action executed the hash-pinned collector from the MSI-owned support directory, returned 0, and automatically created a diagnostic ZIP containing the active MSI log and no reported collection issues. Windows Installer returned the expected 1603, removed its product record and the installation directory, and the fixture never registered the input method. The MSI log in the archive is a snapshot taken during rollback, not the final complete log. A later isolated test also confirms that custom-action error codes are summarized. Failures before support files have been installed, failures outside MSI, rollback-disabled installs, and uninstall failure collection remain unverified. The legacy cleanup scripts are packaged but not yet invoked.

A second interactive fixture changed only the target directory so that the verified preflight failed before InstallFiles. Windows Installer returned 1603 with no product record or installation root, and the MSI Binary collector produced a ZIP and removed its protected staging directory. The active log snapshot did not yet contain the triggering error, so the collector now receives the failure stage and HRESULT directly. An isolated MSI-Binary test with an intentionally incomplete log verifies the summary contains `prepare-root` and `0x80070057`; the revised end-to-end interactive fixture remains to be rerun.

The MSI now schedules a narrow legacy-orphan action after InstallFiles and before registration. It skips when both exact legacy leaves are absent; a partial or unverified state fails closed. When both leaves exist, the action locks and verifies the build-pinned MSI support files, manifest and helper before launching the recovery script. The script revalidates the complete prepared-root file set before each observation, then uses the existing durable backup and conditional registry transaction. An isolated registry integration test confirms a changed file prevents any deletion and a verified fixture creates a backup before removing its two test leaves. The interactive clean-install test observed the no-op path; a real machine with an orphan has not yet exercised this newer packaged path.

A combined interactive test subsequently verified early failure collection, the explicit failure stage and HRESULT in the ZIP, successful clean installation and successful uninstall. The MSI and installation directory were absent afterward. Diagnostic collection is best effort and cannot cover failures before its MSI custom actions run or guarantee output if rollback is disabled or the collector fails.
